# 人員主檔匯入 SFT 生產日報表

## 1. Problem Statement

bonus-system 的「人員主檔管理」目前只能一筆一筆手動新增人員，員工代號是內部自行編的序號（`00001`～`00016`），跟公司 ERP／MES 系統匯出的「SFT 生產日報表(人員)」裡使用的真實員工代號（例如 `000051`）完全對不上——這兩套代號其實指向同一批真人，只是編號系統不同。同時，SFT 報表裡還有幾位在 bonus-system 完全沒有建檔的新進人員。目前沒有任何機制可以用這份報表批次校正既有人員的代號、或批次建立新人員，只能逐筆手動處理，容易漏掉或打錯。此外，新增人員／設為離職目前僅限 developer 操作，實務上班長也需要能處理這類人員資料異動。

## 2. Scope（本次範圍）

- **In scope**：
  - 人員主檔管理頁面新增「匯入 SFT 報表」入口，上傳 xls 檔案
  - 僅解析報表中的「員工代號」「姓名」兩欄，其餘欄位（數量、機台等）本次不使用
  - 依比對規則將匯入資料分類為「取代」「新增」「無法匯入」，產生一次性批次預覽清單
  - 預覽清單逐筆可勾選（預設未勾選），使用者確認後才套用已勾選項次
  - 既有「新增人員」「設為離職」的操作權限，由 developer-only 放寬為 foreman + developer
  - 新功能「匯入套用」的操作權限：foreman + developer
- **Out of scope**：
  - 報表中的「數量」（生產數量／實際產量）自動帶入出勤表單——是另一個獨立構想，不併入本次
  - 重複匯入時「已略過、之後不再提示」的追蹤機制（匯入為低頻操作，不需要）
  - 同一份報表中兩筆匯入資料指向同一位現有人員的特殊提示（邊界情況，暫不處理）
  - 一筆匯入資料同時分別符合兩位不同現有人員（代號符合 A、姓名符合 B）的判定規則（邊界情況，暫不處理）
  - 已離職（`status: terminated`）人員之間或離職人員與在職人員的比對（離職人員一律不列入比對範圍，見 FR-3）

## 3. Functional Requirements

- **FR-1**：人員主檔管理頁面新增「匯入 SFT 報表」檔案選擇入口，位於既有「新增人員」表單下方、人員列表上方，沿用頁面既有的行內展開風格（不使用彈窗）。
- **FR-2**：上傳檔案後，系統解析 xls 內容，僅取用「員工代號」「姓名」兩欄資料，忽略其他欄位。
- **FR-3**：比對範圍限定「在職」（`status: active`）人員，依序判定每筆匯入資料：
  - 員工代號與姓名皆與某位在職人員相符 → 不列入預覽清單（無異動）
  - 員工代號或姓名恰有一項與某位在職人員相符（非兩項皆符合）→ 標示「取代」
  - 員工代號與姓名皆不符合任何在職人員 → 標示「新增」
  - 若「新增」候選的員工代號恰與某位離職人員現有的員工代號相同 → 改標示「無法匯入」，附衝突原因（占用者姓名）
- **FR-4**：「取代」項次的更新規則：員工代號相符時，更新該人員的姓名為匯入值、代號不變；姓名相符時，更新該人員的員工代號為匯入值、姓名不變。
- **FR-5**：預覽清單以行內表格呈現，每筆項次顯示分類標籤（取代／新增／無法匯入）、現有資料與匯入資料對照，並附一個勾選框，預設「未勾選」；「無法匯入」項次的勾選框為停用狀態，不可勾選。
- **FR-6**：預覽畫面提供「確認套用」與「取消」兩個按鈕。「確認套用」只執行已勾選項次對應的動作（更新既有人員或建立新人員），未勾選項次不產生任何資料異動；「取消」直接關閉預覽區塊，不寫入任何資料。
- **FR-7**：既有「新增人員」（`POST /api/persons`）與「設為離職」（`DELETE /api/persons/[employeeId]`）的權限由 developer-only 放寬為 foreman + developer 皆可操作。
- **FR-8**：新增的「匯入套用」操作，權限為 foreman + developer 皆可操作。

## 4. Acceptance Criteria

AC-1：匯入入口顯示於人員主檔管理頁面
- Given：使用者在人員主檔管理頁面
- When：頁面載入完成
- Then：畫面顯示「匯入 SFT 報表」檔案選擇入口，位於既有新增人員表單下方、人員列表上方

AC-2：姓名相符、代號不符 → 判定為取代
- Given：SFT 報表中某筆資料的姓名與某位在職人員相符，但員工代號不同
- When：使用者上傳該報表
- Then：預覽清單出現一筆標示「取代」的項次，顯示該人員現有的員工代號與匯入的員工代號

AC-3：代號相符、姓名不符 → 判定為取代
- Given：SFT 報表中某筆資料的員工代號與某位在職人員相符，但姓名不同
- When：使用者上傳該報表
- Then：預覽清單出現一筆標示「取代」的項次，顯示該人員現有的姓名與匯入的姓名

AC-4：代號與姓名皆相符 → 不列入清單
- Given：SFT 報表中某筆資料的員工代號與姓名皆與某位在職人員相符
- When：使用者上傳該報表
- Then：該筆資料不出現在預覽清單中

AC-5：代號與姓名皆不符 → 判定為新增
- Given：SFT 報表中某筆資料的員工代號與姓名皆不符合任何在職人員
- When：使用者上傳該報表
- Then：預覽清單出現一筆標示「新增」的項次，顯示匯入的員工代號與姓名

AC-6：離職人員不列入比對範圍
- Given：某位離職人員的員工代號或姓名恰與 SFT 報表中某筆資料相符
- When：使用者上傳該報表
- Then：該筆資料的比對結果視為與在職人員皆不相符，依 AC-5 或 AC-7 規則判定，不會被當成該離職人員的「取代」項次

AC-7：新增候選與離職人員代號衝突 → 判定為無法匯入
- Given：SFT 報表中某筆資料依 AC-5 規則會被判定為「新增」，但其員工代號恰與某位離職人員現有的員工代號相同
- When：使用者上傳該報表
- Then：預覽清單出現一筆標示「無法匯入」的項次，附上衝突原因（占用者姓名），該項次的勾選框為停用狀態

AC-8：預覽項次預設未勾選
- Given：預覽清單已產生，包含可勾選的項次
- When：使用者檢視清單
- Then：每一筆可勾選的項次（取代、新增）預設皆為「未勾選」狀態

AC-9：確認套用只執行已勾選項次
- Given：預覽清單中使用者已勾選部分項次、部分項次未勾選
- When：使用者點擊「確認套用」
- Then：系統只對已勾選項次執行對應動作（更新既有人員資料或建立新人員），未勾選項次不產生任何資料異動

AC-10：取代動作正確更新對應欄位，且不影響出勤歷史
- Given：一筆「取代」項次因姓名相符、代號不符而產生，使用者已勾選
- When：使用者點擊「確認套用」
- Then：該筆現有人員的員工代號被更新為匯入值，姓名維持不變；該人員既有的出勤紀錄（`AttendanceRecord`）不受影響、仍可正常查詢

AC-11：取消不寫入任何資料
- Given：預覽清單已產生，使用者可能已勾選部分項次
- When：使用者點擊「取消」
- Then：預覽區塊關閉，資料庫沒有任何新增或更新，人員列表維持匯入前的狀態

AC-12：班長可執行匯入套用
- Given：使用者以班長（foreman）角色登入
- When：該使用者在預覽畫面點擊「確認套用」
- Then：操作成功執行，不回傳權限錯誤

AC-13：班長可新增人員（既有功能權限放寬）
- Given：使用者以班長（foreman）角色登入
- When：該使用者透過既有「新增人員」表單送出
- Then：操作成功執行，不回傳權限錯誤

AC-14：班長可將人員設為離職（既有功能權限放寬）
- Given：使用者以班長（foreman）角色登入
- When：該使用者點擊某位在職人員的「設為離職」
- Then：操作成功執行，不回傳權限錯誤

## 5. Non-Functional Requirements（NFR）

NFR-1：預覽階段不得寫入資料庫 — 標準：從上傳檔案到產生預覽清單的過程中，呼叫的函式或 API 不得包含任何 `prisma.person.create` 或 `prisma.person.update` 呼叫，只有「確認套用」之後才允許寫入。

NFR-2：套用動作需具備交易一致性 — 標準：「確認套用」對多筆已勾選項次的新增／更新動作，包在單一資料庫交易（`prisma.$transaction`）內執行，避免部分成功、部分失敗導致清單與實際資料庫狀態不一致。

## 6. Open Questions

- 本次規劃與測試僅確認過 `.xls`（BIFF8 二進位格式）能正確解析；若未來 SFT 報表改用 `.xlsx` 匯出，欄位解析邏輯是否需要同時相容兩種副檔名，尚待實際遇到時再評估。
- 上傳檔案內容不符預期格式（例如找不到「員工代號」或「姓名」欄位標題）時的錯誤訊息內容，本次未明確定義，暫定顯示通用的「檔案格式無法解析」錯誤，不特別客製化。
