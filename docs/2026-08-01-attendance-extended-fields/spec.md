# 出勤表單擴充欄位（加班時數／配合度／3S表現／實際產量）

## 1. Problem Statement

現場目前以 Excel 手工填寫出勤獎金相關資料，欄位包含出勤類別、加班時數、配合度、3S表現、產量等，資料分散於各班長手中的表格、無版本控管、也無法追溯審核歷程。bonus-system 現有的出勤表單（`AttendanceForm` / `AttendanceRecord`）已支援出勤類別＋備註的填寫與 草稿／待審／核准／退回／作廢重審 流程，但尚未收集加班時數、配合度、3S表現、實際產量這四項資料，也沒有「出勤狀態未確認時，其他欄位不應被填寫」的資料完整性保護。本次目標是將 Excel 表單中的欄位對應進現有系統的填寫／審核流程，主要使用者是負責填表的班長與負責審核的開發者／主管，同時讓資料結構乾淨到足以在未來的權重評分需求上直接擴充，而不需要回頭遷移既有資料。

## 2. Scope（本次範圍）

**In scope**
- 新增「配合度」「3S表現」兩張可管理清單資料表，結構比照現有 `AttendanceCategory`（`code / name / sortOrder / isActive`）
- 出勤類別／配合度／3S表現三個清單的管理介面整合為同一頁面，以子分頁切換；配合度／3S表現支援新增／編輯／排序／停用，**出勤類別維持現狀**（僅能停用／啟用，新增/編輯需修改 `scripts/seed.cjs` 並經 code review，不在本次開放範圍）
- `AttendanceRecord` 新增四個欄位並串接進既有表單填寫／審核流程：
  - 加班時數（下拉，1–10 整數，無 0 選項，預設未選）
  - 配合度（下拉 → 配合度清單，允許不選）
  - 3S表現（下拉 → 3S表現清單，允許不選）
  - 實際產量（數字，僅允許正整數，非必填）
- 出勤類別為「未填」時，鎖定同一列其餘所有欄位（含備註）為不可編輯，前端與後端行為一致
- 出勤類別由已選改回未選時，清空同一列其餘欄位（含備註）已填資料

**Out of scope**
- 任何評分／權重計算邏輯，包含三張分類清單（出勤類別／配合度／3S表現）的 `score` 欄位
- 加班時數、實際產量等數字型欄位的級距或公式換算
- 配合度／3S表現的複選功能
- 表單 UI 比照 Excel 的顏色圖例／視覺樣式

## 3. Functional Requirements

- FR-1：類別管理頁面以子分頁方式整合出勤類別、配合度、3S表現三份清單；配合度、3S表現子分頁具備新增／編輯／排序／停用功能，出勤類別子分頁維持現狀僅提供停用／啟用操作。
- FR-2：新增「配合度」「3S表現」資料表與對應 CRUD API，結構比照 `AttendanceCategory`，不含分數欄位。
- FR-3：出勤表單填寫頁新增「加班時數」欄位，下拉選項為未選＋1–10整數，無 0 選項。（**AMENDED 2026-08-04**：上限擴大為 12，見 `docs/2026-08-04-attendance-scoring-rules/spec.md`）
- FR-4：出勤表單填寫頁新增「配合度」「3S表現」下拉欄位，選項來自對應管理清單，皆允許不選。
- FR-5：出勤表單填寫頁新增「實際產量」數字欄位，僅接受正整數，非必填。
- FR-6：出勤類別為未選（null）時，同一列的加班時數、配合度、3S表現、實際產量、備註皆鎖定為不可編輯。
- FR-7：出勤類別由已選改為未選並儲存時，同一列其餘欄位（加班時數、配合度、3S表現、實際產量、備註）資料清空為 null。
- FR-8：鎖定與清空規則需同時在前端 UI 與後端 API（`PATCH /api/forms/:id/records` 或其後續實作）生效，不可僅靠前端限制。

## 4. Acceptance Criteria

AC-1：類別管理頁面顯示三個子分頁，出勤類別維持既有唯讀限制
- Given：使用者進入類別管理頁面
- When：切換「出勤類別」「配合度」「3S表現」三個子分頁
- Then：配合度、3S表現子分頁具備新增／編輯／排序／停用功能；出勤類別子分頁僅維持既有的停用／啟用操作，不提供新增或編輯（新增出勤類別仍須修改 `scripts/seed.cjs` 並經 code review）

AC-2：配合度／3S表現清單可管理且不含分數欄位
- Given：開發者在「配合度」或「3S表現」子分頁新增一筆選項
- When：輸入 code／name 並儲存
- Then：該選項出現在出勤表單填寫頁對應的下拉清單中，且該清單資料結構不含任何分數／權重欄位

AC-3：加班時數下拉為 1–10 整數、無 0 選項、預設未選（**AMENDED 2026-08-04**：上限由 10 擴大為 12）
- Given：表單填寫頁面中，某人員的出勤類別已選
- When：開啟該人員的加班時數下拉選單
- Then：選項僅包含「未選」與 1 到 12 的整數，沒有 0 這個選項，且預設狀態顯示未選（原上限為 10，因假日加班積分規則需涵蓋超過 8 小時的情境，2026-08-04 擴大至 12，見 `docs/2026-08-04-attendance-scoring-rules/spec.md`）

AC-4：配合度／3S表現允許不選
- Given：出勤類別已選
- When：使用者不對配合度或3S表現欄位做任何選擇並儲存
- Then：對應欄位值為 null，且不會被系統判定為錯誤或阻擋送出

AC-5：實際產量僅接受正整數
- Given：出勤類別已選
- When：使用者在實際產量欄位輸入 0、負數、小數或非數字內容
- Then：系統拒絕儲存並提示格式錯誤；輸入正整數（如 1、50）時可正常儲存

AC-6：出勤類別未填時鎖定同列其他欄位
- Given：某人員該列的出勤類別為未選（null）
- When：使用者檢視或嘗試編輯該列
- Then：加班時數、配合度、3S表現、實際產量、備註皆呈現不可編輯狀態

AC-7：出勤類別改回未選時清空同列其他欄位
- Given：某人員該列出勤類別已選，且加班時數／配合度／3S表現／實際產量／備註至少一項已填值
- When：使用者將該列出勤類別改回未選並儲存
- Then：該列加班時數、配合度、3S表現、實際產量、備註全部被清空為 null

AC-8：後端拒絕繞過鎖定規則的寫入
- Given：某人員該列出勤類別為未選（null）
- When：客戶端直接呼叫表單記錄更新 API，嘗試寫入非空的加班時數／配合度／3S表現／實際產量／備註
- Then：API 拒絕該筆欄位寫入（回傳錯誤或忽略非空值，僅保留 null），不會被寫入資料庫

## 5. Non-Functional Requirements（NFR）

- NFR-1：鎖定／清空規則須同時在前端與後端生效 — 標準：對「出勤類別為空但其他欄位非空」的任何 API 請求，後端一律拒絕或忽略該筆非法欄位值，不依賴前端限制作為唯一防線（對應 AC-8）。
- NFR-2：新增欄位不影響既有資料 — 標準：四個新欄位皆為可為 null 的欄位，既有已核准／已送審表單的既有記錄可正常讀取與顯示，不需回填資料即可通過既有測試。

## 6. Open Questions（已於確認階段解答，保留記錄）

- OQ-1（已解）：配合度／3S表現子分頁的管理權限與出勤類別一致，僅開發者角色可新增／編輯／停用——與現有 `requireRole("developer")` 的權限模型相同，新增的兩張清單比照辦理。
- OQ-2（已解）：只要出勤類別非空即解鎖全部欄位，不因類別種類而有差異；加班時數／配合度／3S表現／實際產量皆不設必填限制，「有資料」與「無資料」的差異只影響未來加權分數，本次不因此增加額外的欄位級限制規則。
- OQ-3（已解）：權重評分系統將於未來另開獨立功能分頁/需求實作，與本次的表單填寫功能保持解耦，本次不預留任何評分相關欄位或介面。
