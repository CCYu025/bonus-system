# 出勤表單匯入 SFT 生產日報表

> **修訂記錄（2026-08-11，開發完成並驗收通過後、實機測試階段）**：AC-3／AC-4／AC-5／AC-12 與 FR-3～FR-5 修訂——原設計要求依「生產日期」欄位過濾比對範圍（只取等於表單日期的資料列）。實機測試時使用者回報：夜班存在跨日情況，SFT 系統記錄的「生產日期」不可靠地對應到出勤表單所屬日期（例如晚班在隔天凌晨才報工，生產日期會被記成隔天），依此欄位過濾會把實際屬於當天班次的產量錯誤排除，實測時已重現此問題（一份僅含隔天日期的報表被正確地全數判定為查無資料，但這其實是不該過濾掉的情境）。修訂後比對範圍改為整份上傳檔案，僅依「員工代號」＋「姓名」比對加總，不再解析或使用「生產日期」欄位。修訂前的版本見 git 歷史（commit `2f8051c`）。

## 1. Problem Statement

班長目前在出勤表單詳細頁（`src/app/forms/[id]/page.tsx`）填寫每位人員的「實際產量」欄位時，須自行對照 SFT 生產系統匯出的 Excel 日報表，手動加總每位人員當天的產量並逐一輸入，容易出錯也耗時。本功能讓班長可直接上傳 SFT 匯出的 Excel 檔，由系統依員工代號加總「數量」欄後，自動帶入表單中對應人員的「實際產量」欄位，班長只需確認與必要時人工處理少數對不上的資料。

## 2. Scope（本次範圍）

- **In scope**：
  - 出勤表單詳細頁新增「匯入SFT生產日報表」按鈕與上傳流程
  - Excel 解析：定位表頭列、跳過殘留重複表頭列、依員工代號加總數量（不依生產日期過濾，見下方修訂記錄）
  - 匯入對象篩選（依表單當下有效出勤類別）
  - 工號/姓名雙欄比對邏輯與五類分類結果
  - 確認摘要畫面呈現分類結果，套用至前端未儲存的編輯狀態（`edits` state）
  - 表單狀態與角色權限限制

- **Out of scope**：
  - 自動監看/讀取固定資料夾路徑（本次為手動上傳）
  - 對 Person 主檔的任何寫入或修正（沿用既有「人員主檔匯入 SFT 生產日報表」功能，不重疊）
  - needsReview 清單項目的系統代為套用機制（班長仍是透過既有的實際產量輸入框手動填寫，系統只負責呈現清單供參考）
  - 匯入歷程/稽核記錄的另建報表（沿用既有表單「異動軌跡」機制與否，留待實作階段依現有 audit log 慣例決定）

## 3. Functional Requirements

- **FR-1**：在出勤表單詳細頁新增「匯入SFT生產日報表」按鈕，位置在「儲存草稿」按鈕左側（順序：匯入SFT生產日報表／儲存草稿／確認送出待審）。
- **FR-2**：提供檔案上傳介面，接受 SFT 匯出的 Excel（.xls/.xlsx）檔案。
- **FR-3**：解析 Excel 時以內容定位表頭列（尋找「員工代號」「姓名」「數量」等欄名），跳過表頭前的標題列與資料中殘留的重複表頭列。
- **FR-4（AMENDED 2026-08-11）**：不依「生產日期」欄位篩選資料列——夜班跨日會使生產日期不可靠地對應到表單所屬日期（見上方修訂記錄），比對範圍為整份上傳檔案中的所有資料列。
- **FR-5（AMENDED 2026-08-11）**：依「員工代號」將整份檔案中的資料列「數量」欄加總，得到每個員工代號的產量總和（不限生產日期）。
- **FR-6**：匯入對象僅限表單中「當下有效出勤類別」為「正常出勤」或「假日加班」的人員；有效出勤類別取自前端尚未儲存的編輯狀態（`edits`），若該人員無未儲存編輯則以表單已存的類別為準。
- **FR-7**：以「員工代號＋姓名」雙欄比對 Excel 資料列與表單人員名單，將比對結果分類為 `matched`／`needsReview`／`skippedWrongCategory`／`noExcelData`／`unmatchedInExcel` 五類，並回傳結構化清單（非僅總數字）。
- **FR-8**：匯入 API 為唯讀操作，僅解析、過濾、比對、分類，不對資料庫執行任何寫入。
- **FR-9**：前端呼叫匯入 API 時，須一併送出目前畫面上每位人員的有效出勤類別，供後端分類判斷使用。
- **FR-10**：確認摘要畫面呈現五類分類結果，其中 `matched` 若會覆蓋既有非空的實際產量值，需明確標示「將被覆蓋」與新舊值對照；使用者確認後，`matched` 清單的數量才寫入前端 `edits` state 的實際產量欄位。
- **FR-11**：匯入操作僅限表單狀態為 `draft` 或 `rejected` 時可執行，前端與後端 API 皆須限制。
- **FR-12**：匯入操作的角色權限，與既有表單記錄編輯權限（`PATCH /api/forms/:id/records`）一致，不另外放寬或收緊。

## 4. Acceptance Criteria

**AC-1：按鈕位置與可見性**
- Given：班長開啟狀態為 `draft` 或 `rejected` 的表單詳細頁
- When：頁面渲染完成
- Then：「匯入SFT生產日報表」按鈕顯示在「儲存草稿」按鈕左側，三個按鈕由左至右順序為：匯入SFT生產日報表／儲存草稿／確認送出待審

**AC-2：其餘狀態不可匯入（前端）**
- Given：表單狀態為 `pending_review`、`approved` 或 `voided`
- When：檢視表單詳細頁
- Then：不顯示「匯入SFT生產日報表」按鈕，或按鈕呈停用狀態，無法觸發匯入

**AC-3（AMENDED 2026-08-11）：不依生產日期過濾，僅依員工代號＋姓名比對整份檔案**
- Given：上傳的 Excel 檔案內含同一員工代號橫跨多個生產日期的資料列（例如夜班跨日，同一人的資料同時記錄成 2026-08-06 與 2026-08-07 兩個生產日期）
- When：對任一日期的表單執行匯入
- Then：系統加總整份檔案中該員工代號的所有資料列，不依「生產日期」欄位篩選——原因是夜班跨日會使生產日期不可靠地對應到表單所屬日期，依生產日期過濾會誤將實際屬於當天班次的產量排除在外（原始版本的過濾行為見 git 歷史 commit `2f8051c`）

**AC-4（AMENDED 2026-08-11）：表頭定位與重複表頭列跳過**
- Given：Excel 檔案表頭列前有標題列，且資料列中間夾雜一列內容與表頭相同的殘留重複表頭列
- When：系統解析該檔案
- Then：系統以內容定位真正的表頭列（含「員工代號」「姓名」「數量」等欄名，不再要求「生產日期」欄名存在），並將該殘留重複表頭列排除，不當成一筆有效資料參與加總

**AC-5（AMENDED 2026-08-11）：依員工代號加總整份檔案的數量**
- Given：上傳的檔案中，同一員工代號存在多筆資料（不同工單/機台，可能橫跨不同生產日期）
- When：系統執行加總
- Then：該員工代號的加總結果，等於整份檔案中所有屬於該員工代號的資料列「數量」欄總和，不受生產日期限制

**AC-6：有效出勤類別以未儲存編輯為準**
- Given：班長已在畫面上將某人員的出勤類別改為「正常出勤」，但尚未按下「儲存草稿」
- When：班長執行「匯入SFT生產日報表」
- Then：系統以畫面上當下（尚未儲存）的有效出勤類別判斷該人員是否為匯入對象，而非資料庫中已存的舊值

**AC-7：非目標類別歸為 skippedWrongCategory**
- Given：某人員目前有效出勤類別為「事假」（非正常出勤／假日加班）
- When：執行匯入，且該人員的員工代號在報表中查有當天資料
- Then：該人員歸類為 `skippedWrongCategory`，不自動套用數量

**AC-8：完全比對成功（matched）**
- Given：報表中某筆資料的員工代號與姓名，皆與表單中某人員當下的工號與姓名相符，且該人員有效出勤類別為正常出勤或假日加班
- When：執行匯入
- Then：該人員歸類為 `matched`，其加總後的產量數字於使用者確認後寫入前端 `edits` state 的實際產量欄位

**AC-8a：加總結果為 0 或異常值時直接套用，不做特殊處理**
- Given：某人員歸類為 `matched`，其加總後的「數量」結果為 0、或因報表資料本身包含非整數／負值而使加總結果不是正整數
- When：使用者於確認摘要畫面按下確認套用
- Then：系統照樣將該加總結果原值寫入前端 `edits` state 的實際產量欄位，不做四捨五入、排除、歸零或另行分類；若該值不符合既有「實際產量必須為正整數」的儲存驗證（`saveFormRecords`），則沿用該既有驗證機制，於使用者按下「儲存草稿」／「確認送出待審」時依現有規則擋下並提示，匯入流程本身不重複做這層驗證

**AC-9：工號符合、姓名不符 → 需人工確認**
- Given：報表某筆資料的員工代號與表單中某人員的工號相符，但姓名不同
- When：執行匯入
- Then：該筆歸類為 `needsReview`，不自動套用數量；確認摘要清單顯示報表原始工號／姓名／加總數量，以及對應到表單中的候選人員姓名

**AC-10：姓名符合、工號不符 → 需人工確認**
- Given：報表某筆資料的姓名與表單中某人員的姓名相符，但工號不同
- When：執行匯入
- Then：該筆歸類為 `needsReview`，不自動套用數量，呈現方式與 AC-9 相同

**AC-11：工號與姓名對應到不同人（衝突）→ 需人工確認**
- Given：報表某筆資料的員工代號對應表單中的人員 A，姓名卻對應表單中的人員 B，且 A 與 B 不是同一人
- When：執行匯入
- Then：該筆歸類為 `needsReview`，確認摘要同時列出候選人 A 與候選人 B，不自動套用數量

**AC-12（AMENDED 2026-08-11）：查無報表資料維持原值**
- Given：某人員有效出勤類別為正常出勤或假日加班，但整份上傳的報表檔案中查無此員工代號的任何資料列
- When：執行匯入
- Then：該人員歸類為 `noExcelData`，其「實際產量」欄位維持原值不變（不論原值為空或非空）

**AC-13：報表資料在表單中完全找不到對應**
- Given：報表某筆資料的員工代號與姓名，皆與表單中任何人員都不相符
- When：執行匯入
- Then：該筆歸類為 `unmatchedInExcel`，於確認摘要中列出僅供告知，不影響表單任何欄位

**AC-14：覆蓋既有數值需標示**
- Given：某人員「實際產量」欄位已有非空值（不論是已存檔的值，或本次會話中已手動輸入尚未存檔的值），且該人員本次匯入結果為 `matched`
- When：檢視匯入確認摘要
- Then：該筆標示為「將被覆蓋」，並同時顯示原值與即將套用的新值；使用者確認套用後才實際覆蓋前端 `edits` state 中的值

**AC-15：匯入 API 為唯讀，不寫入資料庫**
- Given：匯入 API 已完成解析並回傳五類分類結果
- When：使用者尚未於確認摘要畫面按下確認套用
- Then：資料庫中此表單的任何欄位皆未被修改；匯入 API 全程未執行任何資料庫寫入操作

**AC-16：確認套用後仍須手動存檔**
- Given：使用者已於確認摘要畫面按下確認套用，`matched` 清單的數量已寫入前端 `edits` state
- When：使用者尚未按下「儲存草稿」或「確認送出待審」
- Then：資料庫中的表單資料維持不變，變更僅存在於前端未儲存狀態，直到既有的儲存/送審流程被觸發

**AC-17：表單狀態限制（後端）**
- Given：表單狀態為 `pending_review`、`approved` 或 `voided`
- When：使用者（或繞過前端）直接呼叫匯入 API
- Then：系統拒絕該請求並回傳明確錯誤，不論前端按鈕是否已隱藏或停用

**AC-18：權限沿用既有編輯權限**
- Given：目前登入使用者的角色不具備編輯此表單記錄的權限
- When：呼叫匯入 API
- Then：系統拒絕該請求，權限檢查結果與呼叫既有 `PATCH /api/forms/:id/records` 時一致

**AC-19：手動上傳，非自動監看資料夾**
- Given：使用者點擊「匯入SFT生產日報表」按鈕
- When：系統呈現匯入操作介面
- Then：呈現的是檔案選擇上傳介面（如檔案選取對話框），系統不會自動讀取或監看任何本機／雲端固定資料夾路徑

## 5. Non-Functional Requirements（NFR）

- **NFR-1**：匯入 API（解析／過濾／比對／分類）不得對資料庫執行任何寫入操作 — 標準：程式碼審查／測試可驗證該路由的實作中不存在任何 Prisma `create`/`update`/`delete`/`upsert` 呼叫。
- **NFR-2**：檔案格式無法解析（找不到表頭列、檔案損毀等）時，須回傳明確的繁體中文錯誤訊息，風格與既有 `parseSftReport`（`AppError(400, "檔案格式無法解析")`）一致 — 標準：對應錯誤情境有測試覆蓋。
- **NFR-3**：後端須驗證前端傳入的「有效出勤類別」僅適用於此表單當前的人員名單（不可讓請求內容指定表單以外的人員或不存在的 `categoryId`）— 標準：對非法輸入（不在名單中的人員、不存在的 categoryId）有測試覆蓋並回傳明確錯誤，不因此造成分類結果錯誤或例外未處理。
