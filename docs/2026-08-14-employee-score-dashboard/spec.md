# 員工分數查詢儀表板

## 1. Problem Statement

目前系統的積分資料只能透過 `/query/score`（需要 `foreman`/`developer` 登入帳號）查詢，產線員工本人沒有任何管道自己查看當月積分狀態與排名，必須透過班長代查或口頭/紙本公告。本功能讓員工在不擁有系統帳號的情況下，直接瀏覽當月所有計分人員（不超過 20 人）的積分排行與明細，降低查詢門檻，同時不需要為每位員工開通個人登入帳號。

考核人數規模小（≤20 人），使用者已確認採「開放瀏覽」模式，而非原先討論的「只看自己＋前 N 名區間」——任何人造訪此頁即可看到當月所有人的總分排名，並點選任一人開啟彈窗查看該人員的分數組成甜甜圈圖與每日分數明細，效果上等同既有 `/query/score` 頁面的完整呈現方式，只是拿掉登入門檻、並改用彈窗呈現個人資料（原先討論的行內展開方式對整月資料而言畫面會撐太高、不好收合，故改為彈窗）。頁面上另外提供一張跨人比較的分數組成堆疊長條圖，方便一眼看出排名靠前的人是哪些項目撐起來的。

## 2. Scope（本次範圍）

- **In scope**：
  - 一個免登入即可存取的頁面，載入後直接顯示當月所有計分人員的總分排行榜（依總分排序），不需輸入工號或任何條件即可看到完整清單
  - 點選任一人員開啟彈窗，顯示該人員的分數組成甜甜圈圖（五項分數，總分置中）與每日分數明細（出勤類別分／加班分／配合度分／3S分／SOP分各分項 + 當日小計），彈窗高度固定、明細表格區域可獨立捲動
  - 排行榜頁面上另外提供一張跨人比較的分數組成堆疊長條圖（前 N 名，草案 N=8），沿用同一份已取得的排行榜資料，不另外呼叫 API
  - 頁面提供月份選擇器（比照既有 `/query/attendance`、`/query/score` 的 `<input type="month">` 慣例），預設當下月份，可切換查看其他月份的排行榜/圖表/個人明細
  - 以手機/平板（觸控裝置）為主要考量的響應式版面：窄螢幕下排行榜清單精簡欄位、個人資訊改用從底部滑出的操作表（bottom sheet）；同時維持 PC（滑鼠+鍵盤）下的完整欄位表格與置中對話框呈現
  - 分數計算邏輯完全沿用既有 `queryScoresByMonth`（`src/lib/score-query.ts`），不新增分類、不另建計分規則
  - 對應 API 刻意不做任何登入/驗證檢查（使用者已確認的產品決策，見 NFR-1）

- **Out of scope**：
  - 新增「員工」角色或個人帳號登入機制（`prisma/schema.prisma` 的 `UserRole` 不因本功能新增成員）
  - 任何形式的驗證（工號輸入、PIN、生日末四碼等）或查詢頻率限制/防爬蟲機制（使用者已確認不加，見 NFR-1 的風險說明）
  - 排名裁切/區間限制（前次討論的「前 N 名 + 自己區間」已由使用者改為完全開放瀏覽，不再適用）
  - 多月趨勢圖（例如近 6 個月總分折線圖）——月份選擇器只切換單一月份的排行榜/圖表/明細，不做跨月份的趨勢視覺化
  - 舊構想 `demo.html` 中「產量」「品質」「補償」等分類與多來源自動匯入/資料透明頁——現行系統無對應資料來源，不在本次範圍
  - 管理端功能（資料匯入狀態、資料編輯等）——已由既有 `/settings`、`/query` 提供，不重做

## 3. Functional Requirements

- **FR-1**：新增一個獨立的公開頁面路由（草案路徑 `/board`，實際命名於 plan 階段定案），與 `/settings`、`/query`、`/forms` 等既有管理頁面完全分開、不掛在其下；此路徑需明確排除在 `src/proxy.ts` 的登入導轉 `matcher` 之外，未登入的瀏覽器造訪時不會被導向 `/login`。首頁（`/`）與其餘既有頁面的 `matcher` 規則維持現狀，不因本功能變成公開。
- **FR-2**：頁面載入時自動呼叫對應的查詢 API，取得所選月份（預設當下月份，見 FR-10）所有計分人員的總分排行榜，該 API 不呼叫 `requireAuth()`/`requireRole()`。
- **FR-3**：查詢 API 回傳的人員名單、五項分數與總分，計算邏輯與既有 `src/lib/score-query.ts` 的 `queryScoresByMonth` 保持一致，不另外實作一套計分規則或名單篩選規則。
- **FR-4**：前端以總分排序（由高到低）顯示完整排行榜（姓名、工號、五項分數、總分），不做人數上限裁切；總分相同時，次要排序依姓名筆畫/字母序（實際排序方式於 plan 階段定案），確保排序結果穩定、每次載入同一份資料時順序一致。
- **FR-5**：使用者點選清單中任一人員時，開啟一個彈窗顯示該人員資訊，關閉方式至少包含：彈窗右上角關閉鈕、點擊背景遮罩、按 `Esc` 鍵；彈窗高度固定（不隨資料筆數無限撐高），內部的每日明細表格區域可獨立捲動。
- **FR-6**：所選月份完全沒有任何計分人員（例如尚無出勤表單資料）時，頁面顯示明確的「該月份尚無資料」提示，而非空白畫面或錯誤畫面；此規則對預設的當下月份與使用者手動切換到的任何月份都成立。
- **FR-7**：首頁（`/`，僅登入使用者可見，行為不變）新增一個連結指向 FR-1 的公開頁面，方便已登入的班長/開發者快速找到、複製網址（例如提供給要在現場平板設定書籤的人）；此連結本身也在登入牆後面，不是員工的實際存取入口。
- **FR-8**：彈窗內容由上到下依序為：人員姓名／工號／當月名次、分數組成甜甜圈圖（五項分數各一色，總分數字置於圖表中央）＋對應圖例（含每項分數數值）、當月每日紀錄明細表格（日期、出勤類別、各分項得分、當日小計）。彈窗內的每日明細表格區域捲動時，表格表頭（日期/出勤類別/各分項/當日小計）以 `sticky` 固定在該區域頂部；當區域尚有未捲動到的內容時，區域底部顯示一段淡出漸層陰影提示，捲到底部時陰影消失。
- **FR-9**：排行榜頁面提供一張分數組成堆疊長條圖，比較目前排行榜前 N 名（草案 N=8，實際數字於 plan 階段定案）人員的五項分數組成；若所選月份符合資格的人員總數少於 N，則顯示全部人員，不視為錯誤。圖表資料直接取自 FR-2 已取得的排行榜回應，不因這張圖表另外呼叫 API 或重新計算；五項分數在堆疊長條圖與 FR-8 的甜甜圈圖之間使用相同的顏色對應（同一項分數在兩張圖表上永遠是同一個顏色）。
- **FR-10**：頁面提供月份選擇器（`<input type="month">`，比照既有 `/query/attendance`、`/query/score` 頁面慣例），預設值為當下月份；使用者切換月份後，排行榜、FR-9 的堆疊長條圖，以及後續開啟的個人彈窗（FR-8）皆改為顯示該月份的資料，不需重新整理頁面，資料來源與計算邏輯仍沿用 FR-3。
- **FR-11**：頁面依螢幕寬度提供兩種版面（實際寬度斷點於 plan 階段定案）：
  - **窄螢幕（觸控裝置為主）**：排行榜清單精簡為排名／姓名／總分三欄（五項分數移除，改在彈窗內呈現）；點選人員時，個人資訊以從畫面底部滑出、佔滿寬度的操作表（bottom sheet）呈現，可透過下滑手勢、點擊背景空白處、或右上角關閉鈕關閉。
  - **寬螢幕（PC 為主）**：排行榜清單顯示完整欄位（姓名、工號、五項分數、總分）；點選人員時，個人資訊以置中對話框呈現，可透過點擊背景、`Esc` 鍵、或右上角關閉鈕關閉（即 FR-5 原有行為）。
  - 兩種版面呈現的資料內容（FR-8 彈窗內容、FR-3 計算邏輯）完全相同，只有版面配置與開啟/關閉互動方式不同。

## 4. Acceptance Criteria

**AC-1：免登入可存取查詢頁**
- Given：使用者（含完全未登入、瀏覽器沒有任何 session cookie）
- When：造訪員工分數查詢頁面
- Then：系統不將其導向 `/login`，直接呈現頁面內容

**AC-2：頁面載入即顯示當月完整排行榜**
- Given：系統中當下月份存在至少一位計分人員（在職人員 ∪ 當月有合格紀錄的人員，沿用 `queryScoresByMonth` 既有名單規則）
- When：使用者造訪頁面
- Then：不需輸入任何條件，畫面直接顯示當下月份所有計分人員依總分排序的排行榜，每筆資料顯示姓名、工號、總分

**AC-3：所選月份無資料時的明確提示**
- Given：目前顯示中的月份（預設當下月份，或使用者切換到的其他月份）沒有任何符合計分名單條件的人員
- When：使用者檢視頁面
- Then：畫面顯示明確的「該月份尚無資料」提示文字，不是例外錯誤畫面、也不是無說明的空白列表

**AC-4：點選人員開啟個人資訊彈窗**
- Given：排行榜中已顯示至少一位人員
- When：使用者點選該人員所在列
- Then：畫面開啟彈窗顯示該人員的分數組成與每日明細（詳見 AC-9、AC-10）；使用者可透過彈窗右上角關閉鈕、點擊背景遮罩、或按 `Esc` 鍵關閉彈窗，關閉後回到排行榜、排行榜本身不受影響

**AC-5：分數與計算方式跟既有查詢頁一致**
- Given：某人員同時可透過本頁面與既有 `/query/score`（登入後）查詢
- When：兩邊皆查詢同一人、同一月份的資料
- Then：五項分數、總分、每日明細內容完全一致，不因免登入而有不同的計算結果

**AC-6：免額外驗證**
- Given：任何造訪此頁面的使用者，不具備任何密碼、PIN 或其他驗證資訊
- When：造訪頁面並瀏覽排行榜
- Then：系統正常顯示當月所有人的分數與排名（此為使用者已確認的產品決策，風險說明見 NFR-1）

**AC-7：瀏覽不建立登入狀態**
- Given：使用者完成一次頁面瀏覽（含展開任意人員明細）
- When：瀏覽流程結束
- Then：系統不因此建立任何 session/cookie，不將這次瀏覽視為一次登入行為，既有 `developer`/`foreman` 的登入模型與人數不受影響

**AC-8：首頁維持登入才可見，並新增指向公開頁面的連結**
- Given：已登入的 `foreman`/`developer` 使用者
- When：造訪首頁（`/`）
- Then：畫面上看得到一個連結指向 FR-1 的公開排行榜頁面；同時，未登入使用者造訪首頁本身仍會被導向 `/login`（首頁的登入門檻不因本功能改變）

**AC-9：彈窗內顯示分數組成甜甜圈圖與置中總分**
- Given：使用者已開啟某人員的個人資訊彈窗
- When：檢視彈窗上半部
- Then：畫面顯示一個甜甜圈圖，環狀部分依五項分數（出勤類別分／加班分／配合度分／3S分／SOP分）中「數值為正」的項目分色呈現各自佔比，圖表正中央顯示該人員的總分數字（total，含負值項目影響後的真實總和）；圖表旁或下方有對應圖例，列出全部五項（含數值為 0 或負數者）的名稱與實際數值，負值以視覺上可辨識的方式標示（例如負號＋不同顏色文字），不因為無法畫進環狀圖就從圖例省略

**AC-10：彈窗明細表格可獨立捲動，彈窗高度不隨資料筆數變化**
- Given：某人員當月的每日紀錄筆數較多（例如接近整月）
- When：使用者開啟該人員的個人資訊彈窗
- Then：彈窗整體高度維持固定上限，超出可視範圍的每日明細列透過表格區域自身的捲動呈現，不會把整個彈窗或頁面撐開；捲動時表格表頭固定在該區域頂部持續可見；區域底部尚有未捲動到的內容時顯示淡出漸層陰影提示，捲到底部時陰影消失

**AC-11：排行榜頁面顯示分數組成堆疊長條圖**
- Given：排行榜已顯示當月計分人員資料
- When：使用者檢視排行榜頁面
- Then：頁面上有一張堆疊長條圖，顯示目前總分前 N 名人員的五項分數組成（每人一條長條，五項分數以不同顏色分段堆疊，顏色對應與 AC-9 甜甜圈圖一致），且圖表數值與排行榜/彈窗顯示的對應人員分數一致；若當月符合資格人員少於 N 人，顯示全部人員

**AC-12：月份選擇器切換資料**
- Given：使用者在頁面上看到月份選擇器（預設值為當下月份）
- When：使用者選擇跟目前不同的月份
- Then：排行榜（AC-2）、堆疊長條圖（AC-11）皆重新載入並顯示該月份的資料，不需重新整理頁面；之後開啟任一人員的個人資訊彈窗（AC-4）也顯示該月份的資料

**AC-13：窄螢幕（觸控裝置）下的精簡清單與底部操作表**
- Given：使用者以窄螢幕（手機/平板）瀏覽頁面
- When：檢視排行榜清單、並點選任一人員
- Then：排行榜清單只顯示排名／姓名／總分三欄；點選後畫面底部滑出操作表（佔滿螢幕寬度）顯示該人員完整資訊（甜甜圈圖＋每日明細）；使用者可透過下滑手勢、點擊背景空白處、或關閉鈕關閉操作表

**AC-14：寬螢幕（PC）下的完整欄位與置中對話框**
- Given：使用者以寬螢幕（PC）瀏覽頁面
- When：檢視排行榜清單、並點選任一人員
- Then：排行榜清單顯示完整欄位（含五項分數）；點選後以置中對話框顯示該人員完整資訊，可透過點擊背景、`Esc` 鍵、或關閉鈕關閉

**AC-15：彈窗鍵盤操作與焦點管理**
- Given：使用者以鍵盤操作頁面（不使用滑鼠/觸控）
- When：透過鍵盤開啟某人員的個人資訊彈窗（不論是底部操作表或置中對話框呈現）
- Then：焦點自動移入彈窗內；`Tab`/`Shift+Tab` 只在彈窗內部的可互動元素間循環，不會跳到背景排行榜；按 `Esc` 或聚焦到關閉鈕並確認可關閉彈窗；關閉後焦點回到原本觸發開啟的那一列，讓使用者能無縫接續操作

## 5. Non-Functional Requirements（NFR）

- **NFR-1（安全，已確認的產品決策）**：本頁面刻意不做任何身份驗證或存取限制——任何能造訪此網址的人都能看到當月所有計分人員（≤20 人）的完整分數、排名與每日出勤明細。這是使用者在需求討論階段已明確確認的取捨（考核人數規模小，工廠現場資訊本就相對透明），非實作疏漏；spec 明確記載這點，未來若要收緊為需獨立提出的新需求 — 標準：程式碼中對應的免驗證 API route 需有註解明確指向本 spec 作為依據，不得被誤認為忘記加 `requireAuth`。
- **NFR-2（正確性一致性）**：查詢與排名所依據的人員名單、分數計算，需與既有 `queryScoresByMonth`（`src/lib/score-query.ts`）完全一致 — 標準：測試可驗證新 API 回傳的名單、五項分數、總分與既有 `/api/score-query/by-month` 回傳的對應項目相等，不重複實作一套計分規則。
- **NFR-3（存取範圍）**：新頁面路徑需明確排除在 `src/proxy.ts` 的 `matcher` 之外；對應的 API route 刻意不呼叫 `requireAuth`/`requireRole` — 標準：程式碼審查可確認此例外有明確註解說明依據（本 spec）；既有需要登入的路由不受影響，既有測試全數維持通過。
- **NFR-4（彈窗無障礙／鍵盤操作，兩種版面共用同一套邏輯）**：個人資訊彈窗（不論 FR-11 的底部操作表或置中對話框呈現）皆需遵循標準對話框無障礙模式：以 `role="dialog"`、`aria-modal="true"`、`aria-labelledby` 指向人員姓名標記；開啟時焦點自動移入、關閉後焦點回到觸發開啟的清單列；所有可點擊的列與按鈕（清單列、彈窗關閉鈕）觸控目標尺寸不小於 44×44px（含內距），降低現場觸控裝置的誤觸機率 — 標準：可完全透過鍵盤（不使用滑鼠/觸控）開啟、瀏覽、關閉彈窗；螢幕閱讀器可正確讀出彈窗標題與內容邊界，不會把背景排行榜內容一併讀出。
